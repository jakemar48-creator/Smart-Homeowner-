# Generic roofing lead delivery

The /roofing page now sends its existing readable quiz answers, contact fields and attribution to the server-only /api/roofing-leads endpoint. The endpoint validates the request and posts JSON to the supplied Smart Homeowner GHL inbound webhook. Errors keep the visitor on the form for retry. Only an accepted webhook response creates a successful receipt and redirects to /thankyou, where Meta Pixel 29610540228543856 tracks Lead. Lead is installed unconditionally on the thank-you page, including direct visits without a receipt. Partner campaign routing is unchanged.

Set the supplied webhook as the required server-only SMART_HOMEOWNER_ROOFING_WEBHOOK_URL secret in the deployment environment. Without it, submission fails with 503. The URL is not committed to Git. For local end-to-end testing, point it to a disposable local receiver. Never send test contact data to production. Run regression checks with node --test tests/roofing-leads.test.mjs and run the project build.

The generic path saves contact details, readable quiz answers and attribution to the existing Supabase leads table before sending to GHL. It links the lead to the active contractors row identified by SMART_HOMEOWNER_CONTRACTOR_SLUG and creates a lead_deliveries record. GHL success or failure updates both records. Storage failure prevents dispatch and keeps the visitor on the form. No new tables or service-area changes are needed. Confirm the exact existing contractor slug before deployment. Existing partner paths are unchanged. The previous generic page explicitly used basePreview, skipped the lead API and stored only a temporary receipt without contact details. Past generic-page submissions are therefore not recoverable from this implementation unless another external system independently captured them. A database check is required to determine whether other partner campaigns stored leads.

Runtime delivery logging includes only an internal reference, HTTP status and error class. It never logs contact fields, request bodies or the webhook URL. A delivery_accepted entry means the endpoint returned success; it does not prove downstream GHL workflow actions created a contact or appointment.
